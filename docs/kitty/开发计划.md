## 1. 仓库审计结论（对 PRD 的修正）

拉下 T3 Code 源码后发现，它已经提供了 PRD 里需要的大部分底座。因此有几项设计可以简化：

| PRD 原设计                             | T3 Code 现状                                                                                                                    | Kitty 的做法                                                                                                        |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 单独做一个 Hardware MCP Server（Q-02） | 服务端已内置 MCP HTTP Server（`apps/server/src/mcp/`），按 toolkit 组织工具（device、preview、worktree 等），所有 Provider 共用 | **不另起 MCP Server**。新增 `mcp/toolkits/hardware`，与 UI 用的 RPC 调用同一个 Effect Service。Q-02 结案            |
| Hardware Runtime 独立进程              | 设备（模拟器）模块 `apps/server/src/device/` 已经是“服务端拥有外设 → RPC 推流到面板 → MCP 给 Agent”的完整模板，并支持远程连接   | 按 `device/` 的结构新建 `apps/server/src/hardware/`，Runtime 跑在**插着开发板的那台机器**的 server 里，天然支持远程 |
| 自建 UI 布局                           | Web 已有右侧面板体系（`RightPanelTabs`、Device 面板、Diff 面板）和终端                                                          | 新增右侧 **Hardware 面板**（设备 / 串口 / 构建 / KiCad 四个子页），不改主布局                                       |
| 全新 RPC                               | 所有跨端类型集中在 `packages/contracts`                                                                                         | 新增 `packages/contracts/src/hardware.ts`                                                                           |
| 移动端                                 | T3 有 React Native 客户端                                                                                                       | **MVP 不做移动端**，只保证 Web + Desktop                                                                            |

建议后续把 PRD 第 4 节架构图的描述同步成上表的方案。

## 2. 代码组织与上游同步策略（应对 R-06）

原则：**Kitty 代码尽量放进新目录，少改上游文件**。这样每次合并 `upstream/main` 时冲突最少。

```
apps/server/src/hardware/            Hardware Runtime（Effect Services）
  HardwareService.ts                 统一入口，RPC 与 MCP 共用
  idf/                               ESP-IDF 适配（检测、build、flash、monitor、错误解析）
  serial/                            串口枚举、租约、按序列号重绑
  kicad/                             kicad-cli 适配（ERC/DRC/BOM/Gerber、网表读取）
  project/                           board.json / pinmap.json / components.json 读写与一致性校验
  permissions/                       权限矩阵、终端危险命令拦截
apps/server/src/mcp/toolkits/hardware/   29 个 Agent 工具（按 PRD 第 7 节）
packages/contracts/src/hardware.ts   RPC / MCP 共享 Schema
apps/web/src/components/hardware/    Hardware 面板 UI
docs/kitty/                          Kitty 自己的文档（与上游 docs/ 分开）
```

需要改动上游文件的地方只有这些，每处都要做到最小：

- 注册点：RPC 路由、MCP toolkit 列表、右侧面板 Tab 列表。
- 品牌：产品名、图标、应用 ID、数据目录。
- 设置项：ESP-IDF 路径、KiCad 路径。

同步节奏：每两周执行一次 `git fetch upstream && git merge upstream/main`，单独开一个 PR，在 CI 通过后合入。

> 包名（`@t3tools/*`）**不改**。改名会导致每次同步都在几百个文件上冲突，且用户看不到包名。

### 4.1 KeyCAP V1 的基础板：ESP32-IOT-KIT

| 项目     | 原板现状                                                                                                                                                         | 对 Kitty 的影响                                                      |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 许可证   | Public Domain                                                                                                                                                    | ✅ 可自由修改、商用，无需署名（建议仍致谢原作者）                    |
| 主控     | ESP32-WROVER-E（经典 ESP32，16 MB Flash + 8 MB PSRAM）                                                                                                           | ⚠️ PRD 全程按 **ESP32-S3** 设计（原生 USB、USB-JTAG、重枚举）        |
| USB      | Type-C + CH340 自动下载                                                                                                                                          | 经典 ESP32 没有原生 USB，无 USB-JTAG，调试需外接 JTAG                |
| 板载外设 | ICM-20600 六轴 IMU、SHT30 温湿度、PCF8563 RTC、红外收发、光敏、2.0" 触摸屏（ST7789V + FT6236U）、TF 卡、18650 电池管理、4 按键 + 触摸键、RS485 / CAN、以太网扩展 | ✅ 自带 IMU，PRD 的 IMU Demo 可直接沿用；外设丰富，适合做 Agent 演示 |
| 设计文件 | 立创 EDA **标准版**                                                                                                                                              | ⚠️ PRD 的 EDA 链路基于 **KiCad**                                     |
| 资料     | 原理图 PDF、交互式 BOM；ESP-IDF **v4.2** 驱动库 easyio-lib-for-esp32（60+ 例程）                                                                                 | 例程需迁移到 ESP-IDF v5.5                                            |
| 尺寸     | 98 × 98 mm                                                                                                                                                       | —                                                                    |
| 最后更新 | 2022-07                                                                                                                                                          | 器件需重新核对在售状态                                               |

**待确认 A · 主控**（建议①）：

1. **换成 ESP32-S3-WROOM-1-N16R8**：与 PRD、ESP-IDF v5.5 和替身板一致；原生 USB 可去掉 CH340，并支持 USB-JTAG 调试。代价是要重画 MCU 部分、重排引脚。外设电路基本可以保留。
2. 保留 ESP32-WROVER-E：硬件改动最少，但 PRD 中的 USB-JTAG、原生 USB 重枚举等需求要改写，替身板也要换成经典 ESP32 板。

**待确认 B · EDA 格式**（建议①）：

1. **迁移到 KiCad**：KiCad 自带立创 EDA 标准版 / 专业版导入器，导入后修整；Kitty 的 EDA 链路仍只做 KiCad（`kicad-cli` 无界面、可脚本化）。
2. 继续用立创 EDA：Kitty 需改为对接立创 EDA 的扩展 API，PRD 第 5.5 节重写；客户端闭源，自动化能力受限。

### 4.4 ESP-IDF 安装方式：一键托管安装（2026-11-06 决策）

目标：用户装好 Kitty 后，不用手动配置任何 ESP-IDF 环境就能编译和烧录。

**为什么不把 ESP-IDF 直接打进安装包**

本机实测（ESP32-S3 只需要其中一部分）：

| 组件                                       | 大小            |
| ------------------------------------------ | --------------- |
| ESP-IDF 框架源码（v5.5）                   | 约 660 MB       |
| Xtensa 工具链（ESP32-S3 编译器，单个版本） | 约 1.1 GB       |
| GDB、OpenOCD 等调试工具                    | 约 300 MB       |
| Python 虚拟环境                            | 约 100 MB       |
| **合计（仅 ESP32-S3）**                    | **约 2–2.3 GB** |

直接打包的问题：

1. 安装包会从约 200 MB 变成 2 GB 以上，而且 Apple 芯片和 Intel 要各打一份。
2. macOS 公证要求包内每个可执行文件都签名，工具链里有上千个二进制文件，发布流程会非常重。
3. ESP-IDF 和 Kitty 只能捆绑升级，修一个 Kitty 的小 bug 也要重新下载 2 GB。
4. GCC 工具链是 GPL 协议，整体再分发需要额外承担源码提供义务。

**方案：Kitty 内置“一键安装”，后台调用乐鑫官方安装器 EIM**

1. **首次启动检测**：`hw_doctor` 发现没有 ESP-IDF 时，Hardware 面板显示“一键安装 ESP-IDF（约 2 GB）”按钮。
2. **静默安装固定版本**：Kitty 自带乐鑫官方的 `eim` 命令行工具，后台执行
   `eim install -i v5.5.x -t esp32s3 -p ~/.kitty/toolchains -n true --do-not-track true`。
   - 只装 ESP32-S3 需要的部分，版本锁定为 Kitty 验证过的版本。
   - 进度显示在 Hardware 面板里。
3. **国内下载加速**：EIM 支持 `--mirror`、`--idf-mirror`、`--pypi-mirror`，安装时会自动选最快的镜像。国内具体用哪个镜像地址待实测。
4. **离线包**：面向教室、工作坊等网络差的场景，提供单独下载的离线包，使用 EIM 官方的 `--use-local-archive`。
5. **复用已有安装**：已经用 EIM 或 VS Code 插件装过 ESP-IDF 的用户，Kitty 读取 `~/.espressif/tools/eim_idf.json` 直接复用，不重复安装。
6. **Python**：ESP-IDF 需要 Python 3.10–3.14，而 macOS 自带的 python3 是 3.9，版本不够，这是安装失败最常见的原因。Kitty 计划自带一个独立的 Python 运行时（约 50 MB），彻底避开这个问题，具体方案待验证。

排期：放在 Sprint 6 发布前完成，计为 P0。在此之前开发阶段继续使用本机已安装的 ESP-IDF。

### 4.5 一个产品一个仓库（monorepo，2026-11-06 决策）

每个产品（如 KeyCAP）是一个独立的 Git 仓库，也是 Kitty 里的一个项目；硬件和固件放在同一个仓库里一起演进：

```text
keycap/                 一个 Git 仓库 = 一个 Kitty 项目
├── hardware/           kicad/（原理图、PCB）、board.json、pinmap.json、components.json
├── firmware/           ESP-IDF 工程
├── manufacturing/      Gerber、钻孔、坐标文件、BOM（导出默认放这里）
├── docs/  tests/
└── project.json  README.md  .gitignore  .gitattributes
```

- “新建硬件项目”创建新仓库（默认放在当前项目旁边，可改位置），`git init` 并首次提交，注册为 Kitty 项目后直接打开。
- 原理图改动与对应的固件改动在同一个提交里，`hw_pin_check` 才能在同一个版本上对照两边。

**注意 2 · exFAT**：`DeDe` 是 exFAT 格式，macOS 会生成大量 `._*` 文件，Git 会把它们当成损坏的对象。已在 `.git/info/exclude` 中忽略。如果 Git 报 `non-monotonic index`，执行：

```sh
find /Volumes/DeDe/Kitty -name '._*' -not -path '*/node_modules/*' -delete
```

依赖安装在 exFAT 上会直接失败，因此仓库已迁到 DeDe 上的 APFS 磁盘映像 `KittyDev.sparsebundle`（上限 60 GB，按实际占用增长）。DeDe 只剩约 19 GB，需关注空间。

## 7.1 实机测试记录（2026-11-05）

被测板：**Waveshare ESP32-S3-Zero**（ESP32-S3 QFN56 rev v0.2，内置 4 MB Flash + 2 MB PSRAM，原生 USB-Serial/JTAG，VID:PID `303a:1001`，串口 `/dev/cu.usbmodem1301`），外接 Adafruit VCNL4040（I2C SDA=GPIO2 / SCL=GPIO3 / INT=GPIO1）。

| 步骤                           | 结果                                       |
| ------------------------------ | ------------------------------------------ |
| `hw_doctor`                    | ✅ 全部通过，识别到串口                    |
| esptool 读芯片 / Flash         | ✅ ESP32-S3，4 MB，MAC `e8:06:90:94:eb:c0` |
| 备份整片 Flash                 | ✅ 4 MB / 51 s（921600 波特率）            |
| ESP-IDF 5.5.5 编译 hello_world | ✅                                         |
| 烧录 + 串口监视                | ✅ 输出 `Hello world!`                     |
| 还原原固件                     | ✅ VCNL4040 程序恢复运行                   |

对后续 Sprint 的输入：

1. **配件授权**：搭载 Apple 芯片的 Mac 默认拦截新 USB 设备，未授权时板子完全不出现。`hw_doctor` 在“无串口”时应提示检查“允许配件连接”、数据线和扩展坞。
2. **Flash 容量要从芯片读取**：示例工程默认按 2 MB 编译，ESP-IDF 运行时会报容量不符。`hw_project_create` 应先读 esptool 的检测结果，再写入 `CONFIG_ESPTOOLPY_FLASHSIZE`。
3. **原生 USB 软复位不掉串口**：通过 RTS 复位时端口保持不变。重枚举（R-05）主要发生在进入或退出下载模式时，Sprint 2 需专门测这种情况。
4. **烧录前自动备份**：备份整片 Flash 只需约 1 分钟，可作为首次烧录陌生板子时的默认保护（对应 PRD 权限要求）。
5. **板型识别**：同为 ESP32-S3，DevKitC-1、S3-Zero 和 KeyCAP 的引脚不同，`board.json` 需要记录板型，Agent 不能只按芯片型号写引脚。
